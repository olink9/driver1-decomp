# Driver 1 decomp

A matching decompilation of **Driver: You Are the Wheelman** (PlayStation, 1999, Reflections), and a
**native PC port** built from it that is **playable** on Linux (see *Playing it on PC*).

*Matching* means C source that compiles back to the **byte-identical** original executable, using the
original compiler. Once the code is C, it can be rebuilt for other platforms. Driver 2 already got this
treatment from [REDRIVER2](https://github.com/OpenDriver2/REDRIVER2). This repo does it for the first game.

> **No game data is included.** You need your own copy of the game. The target is the US release, Rev 1:
> `SLUS_008.42`, sha1 `94b44a84de2f9fa2dcaf120db2e7b3d74bc70d3d`.

## Is anyone else doing Driver 1?

Not that we could find (October 2026). If you searched GitHub for a Driver 1 decomp or PC port, this is what's out there:

**What these numbers cover:**
- The first two tables cover the game code in the main executable; the third adds the overlays. The PsyQ (Sony SDK) library functions come after
  `__main` (0x738F0). They are identified from signatures but not decompiled, since the PC port replaces them.
- The code overlays FRONTEND.BIN, MCARD.BIN, CRED.BIN and IVIEW.BIN are split and matched (third table). The FMV
  player NFMV.EXE is a separate executable with its own copy of the PsyQ libraries: only its 27 game functions
  (`main` 0x80100B14 up to the libraries at 0x80101FA8) are counted; crt0 and the libraries are identified, not decompiled.
- **Near-misses** are complete C files that differ from the original only in small ways, almost always a
  different register choice by the compiler. They already behave like the original. They just aren't proven
  byte-exact yet.
- **Hand-written asm:** 56 routines (mostly GTE 3D-maths code with custom calling conventions, plus a decompressor)
  were written in assembly by Reflections. They are kept as assembly, marked `/* HANDWRITTEN ASM */`, and counted separately.
- **`FAKEMATCH`:** the bytes match, but only through a compiler hint (an empty `asm` statement, an alias name, a `volatile` cast, a
  `do { } while (0)` wrapper or a dead store)
  that the original source almost certainly didn't use. These files are marked and wait for a better C form.

## How a match is verified

There are two independent checks, and nothing counts on an agent's (or a person's) word.

1. **`tools/fnscore.py`** compiles one C file through the original toolchain and diffs the function with
   [objdiff](https://github.com/encounter/objdiff) against the original function. `MATCH 100.0` means zero
   differing instructions. The score is never rounded up.
2. **`tools/linkcheck.py`** links every matched C file into the real build, in place of the original code,
   and compares the resulting executable byte for byte with the original. All relocations resolve through
   the linker; nothing is patched by hand. It also links all passing functions together and checks the
   sha1 of the full executable.

The link check has already caught real problems the per-function scorer missed: two false matches (a
register difference on a relocated instruction) and two hand-written routines that were 4 bytes too long.
All of them were fixed or demoted.

**Toolchain (confirmed):** GCC 2.7.2 (`cdk` build from [decompals/old-gcc](https://github.com/decompals/old-gcc)),
`-O2 -G8`, then [maspsx](https://github.com/mkst/maspsx) emulating aspsx 2.79, with a small patch
(`tools/maspsx-extern-gp.patch`: small externs ≤ 4 bytes are gp-relative, 8-byte ones absolute).
Thirteen compiler builds were tried; only this one matched everything.

## About AI

**This decompilation is being done by AI agents.** Claude models (Anthropic) write the C, run the tools
and iterate. [@olink9](https://github.com/olink9) directs the work and owns the project. Most of the
matching so far was done in a single day by agents working in parallel. Every agent reads
`pilot/AGENT.md`, which collects the compiler patterns they discovered along the way.

What that means for you:
- **The bytes don't care who wrote the C.** A match is checked by the compiler and the link check above,
  not by trusting the author. A function either rebuilds the original executable exactly or it doesn't count.
- **The C is not "the original source".** Like any matching decomp, it is *a* source that compiles to the
  same code. Names, types and structure are best guesses, informed by Driver 2's debug symbols where the two
  games share code.
- **Readability is not there yet.** Per-function files, placeholder names (`func_00020AE4`, `D_00097524`)
  and local struct definitions are expected at this stage. Cleanup into real source files is on the roadmap.
- If you prefer not to use or contribute to AI-assisted projects, that's completely fine. The tools and
  findings here (compiler identification, the maspsx patch, the Driver 2 symbol mapping) may still be useful
  for your own work.

## Playing it on PC

The decompiled game runs as a native Linux or Windows program on [PsyCross](https://github.com/OpenDriver2/PsyCross),
with SDL2 and OpenGL: menus, FMVs, music, the whole Undercover career and the driving games, with keyboard or gamepad.

**You need your own copy of the game:** the US release, Rev 1 (SLUS-008.42), as a disc image. Nothing from the
game is in this repo or downloaded by it, and there are no ready-made builds: everything is made from your disc.

### The quick way: `driver1.sh` (optional)

```sh
git clone https://github.com/olink9/driver1-decomp && cd driver1-decomp
./driver1.sh setup ~/path/to/your/driver1.cue      # once: unpacks your disc and builds the game
./driver1.sh                                       # play (./driver1.sh --window for a window)
```

What it needs: Linux, `python3`, and `podman` or `docker` (most gaming distros and SteamOS have podman).
The build runs in a container, so no compilers or 32-bit packages go onto your system.

What `setup` does, step by step:
1. **Reads your disc image.** A `.cue`/`.bin` rip as it is; a `.chd` is converted first with `chdman`
   (package `mame-tools`). A `.pbp` needs converting to bin/cue first (psxtract or pop-fe); a plain `.iso`
   won't do, because the music and videos need the raw 2352-byte sectors.
2. **Unpacks it into `pcdata/`** and checks it is the right version (sha1 of `SLUS_008.42`). Another version
   gets a clear message, not a broken build.
3. **Copies the executable and the four code overlays to `orig/`** and checks them against the `*.sha1` files.
4. **Builds in a container** (`port/container/Containerfile`: Ubuntu 24.04 with 32-bit SDL2/OpenAL, CMake and
   splat at pinned versions; about 1 GB, downloaded once). The build splits the game's data out of your files,
   compiles the PC program into `play/`, and puts the 32-bit libraries it uses (SDL2, OpenAL and what they need,
   all open source) in `play/lib` as **fallbacks**: at start, your system's own 32-bit copy of each library is
   used whenever there is one, and a bundled one only where it is missing. Your C library and graphics drivers
   are always your system's own. A system that runs Steam has everything else the game needs.

`./driver1.sh` then starts `play/driver1` fullscreen. Saves (`card1.mcd`), settings (`driver1_mods.ini`) and the
log (`driver1.log`) are in `play/`. To update later: `git pull` and run `setup` again.

Options: `./driver1.sh setup <disc> --engine docker` picks the container tool; `--no-container` builds on your
system instead (you need gcc/g++ multilib, CMake, pkg-config, python3-venv and the 32-bit SDL2 and OpenAL
development packages). Everything is in `driver1.sh` and `port/container/`, readable shell.

### Windows: `driver1.cmd` (optional)

```bat
git clone https://github.com/olink9/driver1-decomp
cd driver1-decomp
driver1 setup C:\path\to\your\driver1.cue
driver1
```

`setup` runs once: it unpacks your disc and builds the game. `driver1` plays (`driver1 --window` for a window).
That is a Command Prompt; in PowerShell, type `.\driver1`. Or without a command line: drop your `.cue` onto `driver1.cmd` to set up, then double-click `driver1.cmd` to
play. (No git? GitHub's *Code > Download ZIP* works too.)

What it needs: Windows 10 or 11, 64-bit. `setup` checks for the rest and offers to install what is missing,
saying exactly what and asking first: [MSYS2](https://www.msys2.org) (via `winget`, into `C:\msys64`) with its
32-bit MinGW-w64 compiler, CMake, Ninja and SDL2 (`pacman`), and Python 3 (via `winget`). The game is a native
32-bit Windows program: no WSL, no container.

What `setup` does, step by step (`driver1.ps1`, readable PowerShell):
1. **Checks the tools** (above) and installs the missing ones if you say yes.
2. **Reads your disc image**, unpacks it into `pcdata\` and checks the version, exactly as on Linux (same
   messages for a `.pbp`, a plain `.iso` or another version; a `.chd` needs `chdman.exe` from MAME on your PATH).
3. **Copies the executable and the four code overlays to `orig\`** and checks them against the `*.sha1` files.
4. **Splits the game's data out** with splat, at the versions the Linux container pins (a Python venv in
   `.venv-pc\`).
5. **Builds OpenAL Soft** (the sound library, open source) once into `.deps\` from its source release, checked
   against a pinned sha256: MSYS2 has no 32-bit package of it.
6. **Compiles the PC program** and puts it in `play\` with the DLLs it uses next to it: SDL2, OpenAL and the
   MinGW runtime, all open source, all built or installed on your machine.

`driver1` then starts `play\driver1.exe` fullscreen. Saves (`card1.mcd`), settings (`driver1_mods.ini`) and the
log (`driver1.log`) are in `play\`. To update later: `git pull` and run `setup` again.

### By hand

Every step without the scripts is in `port/README.md` (unpack, split, build, run, plus the debug and test
switches), for Linux and Windows.

How it was checked against the PlayStation original:
- **Lockstep:** the PC build and the PS1 game (in an emulator) run the same input and log the same game state
  every frame. 17 recorded sessions (all 4 cities, the career, the driving games, training, credits, pause and
  replay) match frame for frame, 24,246 frames in total. `tools/pc/compare/` has the tools.
- **Crash and hang sweep** of every game mode, and a run through the whole Undercover career (47 missions).

Known limits: it is a 32-bit build (Linux, and Windows since November 2026; no 64-bit build yet). The 11 unmatched functions run
as C translated from their assembly. One optional PC-only mod ships with it: skip the garage driving test
(toggle on the Undercover screen; see `port/README.md`, *Mods*).

## Building

You need Linux (or WSL/distrobox), Python 3, and your own copy of the game.

```sh
tools/setup.sh                                  # MIPS binutils, splat, maspsx (+patch), old GCCs
# copy SLUS_008.42 from your disc to orig/SLUS_008.42, then:
.venv/bin/python -m splat split fn.yaml         # one asm file per function (scoring targets)
.venv/bin/python -m splat split slus_008.42.yaml
make                                            # rebuilds a byte-identical SLUS_008.42
```

Scoring one function, and the link check:
```sh
.venv/bin/python tools/fnasm.py func_00062DB0                 # target asm + Driver 2 hints
.venv/bin/python tools/fnscore.py func_00062DB0 src/pilot/func_00062DB0.wip.c --diff   # score one draft
.venv/bin/python tools/linkcheck.py --all --tu src/*.c src/*.s       # every source file, byte-compared
.venv/bin/python tools/progress.py                                    # the table above
```

Code overlays (FRONTEND.BIN at 0x1C0000 and MCARD.BIN at 0xE6600, resident together; CRED.BIN and
IVIEW.BIN both at 0x1E0000, never resident together, so each has its own symbol file and neither config
includes the other's; copy them from `\DRIVER\` on the disc to `orig/`). They are built `-G0` (no `$gp` access at all), and references into the
executable resolve through main's ELF (`tools/mainsyms.py` exports its symbols), so build main first:
```sh
make && .venv/bin/python tools/mainsyms.py      # build/main_syms.txt + build/main_syms.ld
for y in frontend mcard cred iview fn_frontend fn_mcard fn_cred fn_iview; do .venv/bin/python -m splat split $y.yaml; done
make overlays                                   # build/FRONTEND.BIN: OK ... build/IVIEW.BIN: OK
.venv/bin/python tools/fnscore.py func_001C2114 src/pilot/frontend/func_001C2114.wip.c   # target found from the symbol
.venv/bin/python tools/linkcheck.py --target frontend -o pilot/linkcheck-frontend.tsv
```
`tools/targets.py` lists the binaries; `--target main|frontend|mcard|cred|iview|nfmv` works in fnscore, linkcheck,
permsetup, mkqueue, nextbatch and progress.

NFMV.EXE (the FMV player that main `Exec()`s, `\DRIVER\NFMV\NFMV.EXE` -> `orig/NFMV.EXE`) is its own PS-X EXE at
0x80100000 with its own gp (0x80126748) and PsyQ libraries; it does not link against main and is built `-G8` like main:
```sh
.venv/bin/python -m splat split nfmv.yaml && .venv/bin/python -m splat split fn_nfmv.yaml
make nfmv                                       # build/NFMV.EXE: OK (also part of `make overlays`)
.venv/bin/python tools/psyqsig.py --target nfmv --apply 430 420 440 410 450 460 470   # library names
.venv/bin/python tools/linkcheck.py --target nfmv -o pilot/linkcheck-nfmv.tsv
```
It shares names with main (`main`, `__main`, the libraries): pass `--target nfmv` to permsetup/fnasm; fnscore takes the
target from a C file under `src/pilot/nfmv/`.

`objdiff-cli` is expected at `~/.local/opt/decomp/objdiff-cli`; set `OBJDIFF` to override. The Driver 2
hints in `fnasm.py` need two optional checkouts, each with its own environment variable:
- `REDRIVER2_GAME`: the `src_rebuild/Game` directory of OpenDriver2/REDRIVER2.
- `D2_SYMBOL_DUMP`: `symbols/spanish_dump.h` from the archived SoapyMan/REDRIVER2 repo.

## Layout

| Path | |
|---|---|
| `src/*.c`, `src/*.s` | the main executable as real source files (C translation units and the hand-written assembly modules), in address order |
| `src/frontend/`, `mcard/`, `cred/`, `iview/`, `nfmv/` | the same for the FRONTEND.BIN / MCARD.BIN / CRED.BIN / IVIEW.BIN overlays and NFMV.EXE |
| `src/pilot/**/*.wip.c` | C drafts of the remaining near-misses; the source files include their original asm (`INCLUDE_ASM`) until they match |
| `include/structs.h`, `frontend.h`, `mcard.h`, `nfmv.h` | shared records (car, cop, pedestrian, mission, model, menu, memory card, movie decoder) with offset checks |
| `include/` | PsyQ types and macros (PsyCross headers, configured for real PSX layouts), `gte.h` |
| `slus_008.42.yaml`, `fn.yaml` | splat configs: baseline build, and one asm file per function |
| `frontend.yaml`, `mcard.yaml`, `cred.yaml`, `iview.yaml`, `nfmv.yaml`, `fn_*.yaml` | the same for the overlays and NFMV.EXE; `symbol_addrs.<overlay>.txt` are their symbols |
| `symbol_addrs.txt` | named symbols (PsyQ library, confirmed names) |
| `pilot/AGENT.md` | the matching guide: toolchain, rules, ~80 compiler patterns learned so far |
| `pilot/queue.tsv` | all 799 game functions, smallest first |
| `pilot/queue-<overlay>.tsv` | the overlays' 362 + 35 + 13 + 23 functions, NFMV.EXE's 27 |
| `pilot/results.tsv`, `pilot/linkcheck.tsv` | every attempt, and the link-check verdicts |
| `pilot/d2map.tsv` | Driver 1 ↔ Driver 2 function pairs (code similarity) |
| `pilot/names-proposed.tsv` | names proposed by the workers (raw); `names-applied.tsv` / `names-rejected.tsv` are the reviewed split |
| `pilot/retry-notes.md` | open problems and leads |
| `pilot/TU-PLAN.md`, `pilot/TU1.md`, `pilot/TU4.md` | how the source files were reconstructed, and the lessons learned |
| `tools/` | scorer, link check, disassembly helper, Driver 2 matcher, PsyQ signature matcher |

## Contributing

**Bug reports for the PC port are very welcome.** Please say what you did and where (city, mission or mode),
what happened, and what the PlayStation version does there if you know. A memory card image (`card1.mcd`) or a
`D1_PAD` input script that reproduces it helps most.

Issues and pull requests are welcome, from people and from people's agents. A PR that adds or changes a
match must pass `tools/linkcheck.py`. Please don't commit anything taken from the game disc. This repo
contains no game data, and `.gitignore` keeps `orig/`, `asm/` and `build/` out.
